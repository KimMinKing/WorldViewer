### 공식 문서로 확인한 조건

- Android Gradle Plugin 8.x는 실행에 JDK 17 이상이 필요하고, IDE와 터미널이 같은 JDK를 쓰도록 맞추는 것이 권장된다. 현재 JDK 21이 선택할 AGP/Gradle 조합과 호환되는지는 프로젝트 버전을 정한 뒤 다시 확인한다: [Android 빌드의 Java 버전](https://developer.android.com/build/jdks)
- 실제 기기 실행에는 휴대폰 개발자 옵션과 USB 디버깅, 연결 승인, Windows에서 필요할 경우 OEM USB 드라이버가 필요하다. Android 11 이상은 같은 네트워크에서 무선 디버깅도 가능하다: [하드웨어 기기에서 앱 실행](https://developer.android.com/studio/run/device)
- SDK 패키지는 Android Studio SDK Manager 또는 Command-line Tools로 관리한다. 현재 설치에는 Command-line Tools가 없으므로 CLI에서 패키지 추가·라이선스 점검이 필요하면 먼저 설치해야 한다: [SDK 명령줄 도구](https://developer.android.com/tools/sdkmanager)
- 설치된 API 36을 쓰려면 공식 표상 최소 Android Studio 2024.3.1 Patch 1과 AGP 8.9.1이 필요하다. API 36.1은 더 새 IDE/AGP가 필요하므로 첫 셸의 기본값으로 자동 채택하지 않는다: [API별 최소 도구 버전](https://developer.android.com/studio/releases)
- AGP 8.13.2는 Gradle 8.13과 JDK 17 이상을 지원하고 Kotlin 2.3용 R8을 포함한다. 현재 조합은 이 호환표에 맞춰 고정했다: [AGP 8.13 릴리스 노트](https://developer.android.com/build/releases/agp-8-13-0-release-notes)
- 2026년 8월 31일부터 Google Play 신규 앱과 업데이트는 API 36 이상을 대상으로 해야 하므로 `targetSdk 36`을 사용한다: [Google Play 대상 API 요구사항](https://developer.android.com/google/play/requirements/target-sdk?hl=ko)
- 2026년 개발자 확인 정책과 무관하게 ADB 개발 설치는 등록 없이 가능하다. 공개 배포 조건은 별도 단계에서 다시 확인한다: [Android 개발자 확인 FAQ](https://developer.android.com/developer-verification/guides/faq)

## 아직 확인하지 못한 사항

- USB ADB 전송 실패가 케이블·포트 문제인지 Windows USB 계층 호환 문제인지. 무선 ADB 개발 경로는 정상이다.
- Android Studio 설치 여부가 다른 경로에 있는지와 현재 IntelliJ에서 Android 개발 지원을 쓸 수 있는지.
- 한국어기초사전 전체 내려받기의 실제 파일 크기와 중국어 소설 표본 역검색 적합도.
- release 유사 빌드의 장시간 성능, 4GB RAM급 기기와 태블릿 결과.
- 공개 앱 이름·영구 앱 ID, 배포 경로, 개발자 표시 이름·연락처·공개 개인정보처리방침 URL과 release 서명 키 운용 방식.

## 실제 기기 실행 경로

1. 휴대폰과 PC를 같은 Wi-Fi에 연결하고 개발자 옵션의 무선 디버깅을 켠다.
2. `adb pair <주소:페어링포트>`와 휴대폰의 일회용 코드로 페어링한다.
3. `adb connect <주소:연결포트>` 후 `adb devices -l`에서 `device` 상태를 확인한다.
4. debug APK를 설치하고 시작·회전·재시작을 확인한다. USB ADB 장애를 해결하기 전까지 기준 기기는 이 경로를 사용한다.

## 미해결 문제

- 영어 선택 기능을 v1 완료 조건에 포함할 시점은 사용자 결정이 필요하다.
- 영구 앱 ID·배포 이름은 공개 배포 준비 전에 확정해야 한다.
- 한국어기초사전은 선택적 보조 자료 후보일 뿐이며 실제 내려받기 크기·오인율은 미확인이다. v1은 사용자 정의 뜻을 기준으로 진행하기로 승인됐다.
- 청사진 파일의 실제 경로와 요청 경로가 다르다. 원본 보존을 위해 현재는 루트 파일을 기준 문서로 연결했다.

## 최근 작업 기록

### 2026-09-26 — Galaxy Z Flip4 benchmark 검증 준비

- 상태: 검증 대기 — 별도 패키지와 입력 준비·잠금 화면 뒤 기동 확인 완료, 실제 화면 조작 대기
- 변경: 앱 코드는 바꾸지 않았다. Galaxy Z Flip4에 비디버그 가능 `dev.worldviewer.benchmark`를 새로 설치하고 Downloads에 50MiB 반복 중국어 fixture를 배치했다. 기존 `dev.worldviewer` 패키지와 데이터는 건드리지 않았다.
- 검증: benchmark APK는 versionCode 1·versionName `0.1.0-dev-benchmark`이고 package flags에 `DEBUGGABLE`이 없다. fixture는 52,428,800바이트·SHA-256 `f94f99a8db19ff79ddebd1b4762acb8de9ebdca193e8b341223d6769ffcad696`으로 에뮬레이터 기준 입력과 같다. 화면이 잠긴 채 콜드 시작은 1,220ms, 내장 fixture 128블록·UTF-16 97,902자의 준비는 4,105ms였고 crash 기록은 없었다. 확인 뒤 앱을 강제 종료했으며 화면은 계속 꺼진 잠금 상태다.
- 기기 확인: Galaxy Z Flip4 `SM-F721N`, Android 16/API 36, One UI 8.0. 배터리 80%, 공유 저장소 여유 약 246.8GiB. 잠금 때문에 50MiB 가져오기와 화면 결과는 확인하지 않았다.
- 미해결 문제: 사용자가 잠금을 해제해야 시스템 파일 선택기, 스크롤, 전체 병음, TalkBack 음성·두 손가락 탐색과 주관적 피로도를 검증할 수 있다. 시험이 끝나면 benchmark 패키지와 Downloads fixture를 제거한다.
- 다음 작업: 휴대폰 잠금 해제 뒤 준비된 fixture를 benchmark 앱으로 가져오고 에뮬레이터와 같은 성능 절차를 실행한다.

### 2026-09-26 — 낮은 압축률 50MiB 원문 백업 측정

- 상태: 완료 — 결정론적 Base64 TXT로 반복 문장 fixture의 과도한 압축률을 보완한 로컬 측정 완료
- 변경: `generate-reader-benchmark-fixture.ps1`에 기본 `RepeatedChinese`를 유지하면서 `DeterministicBase64` 프로필을 추가했다. 고정 seed의 768KiB 난수 입력을 1MiB Base64 행으로 바꿔 정확한 크기와 동일 해시를 재생성한다. 앱 코드는 바꾸지 않았다.
- 검증: 1MiB Base64 fixture를 두 번 만들자 모두 SHA-256 `6b76bb47500391dc966d823261aeb4db1c6e7dcba57b69475e4065c891b4f2d7`였고 엄격한 UTF-8 디코딩을 통과했다. 새 50MiB 입력은 52,428,800바이트·SHA-256 `5b3d52fb9e57b9ac5b1e274bbd0170d30dfbd47b973b7ad7acaad5a711ec707b`이며 508ms에 가져와 68,267블록·UTF-16 52,428,800자로 열렸다. 기존 기본 프로필도 다시 생성해 52,428,800바이트·기존 SHA-256 `f94f99a8db19ff79ddebd1b4762acb8de9ebdca193e8b341223d6769ffcad696`과 일치했다.
- 기기 확인: Android 16/API 36.1 에뮬레이터의 별도 benchmark 패키지. 기존 반복 원문과 새 Base64 원문 두 개를 포함한 백업은 사용자 payload 104,858,735바이트·6개 항목, 실제 ZIP 39,894,485바이트·SHA-256 `a8c2e7583fa99fbd0f395e5fea6c70eff7b765988499f178150177bed988f8de`였다. Base64 원문 항목은 52,428,800→39,713,656바이트(75.75%), 반복 원문은 52,428,800→178,073바이트(0.34%)였다. 목적 파일 등록부터 앱 완료 로그까지 2,260ms였고 약 100ms 폴링에서 같은 `/data` 파일시스템 사용량 증가는 최대 39,356KiB, 완료 뒤 38,872KiB였다. 목적 파일 자체가 약 38,960KiB이므로 관측 최대값은 그 크기와 거의 일치했다.
- 미해결 문제: 시간의 시작점은 저장 버튼 자체가 아니라 MediaProvider의 목적 경로 등록 로그라 전체 사용자 체감보다 짧을 수 있다. 파일시스템 측정은 내부 임시 파일과 공유 저장소 목적 파일이 같은 `/data`에 있어 둘을 분리하지 못하고 약 100ms 사이의 순간 최대값도 놓칠 수 있다. 실제 클라우드 공급자 업로드 크기와 여유 공간 판정은 별도다.
- 다음 작업: Galaxy Z Flip4 잠금을 해제한 상태에서 별도 benchmark APK로 50MiB 콜드 시작·스크롤·전체 병음과 TalkBack 음성 탐색을 실행한다.

### 2026-09-26 — 제한 문서 공급자 백업 실패 회귀

- 상태: 완료 — 제품과 분리된 에뮬레이터 시험 공급자의 읽기 전용·용량 제한·중간 쓰기 실패 확인
- 변경: `test-document-provider`를 독립 Android 앱 모듈로 추가했다. 시스템 파일 선택기에 생성 불가 읽기 전용 루트와, 파일을 만든 뒤 64KiB까지만 보존하고 reliable pipe를 `EPIPE`로 닫는 제한 루트를 제공한다. `app`은 이 모듈에 의존하지 않으며 제품 APK·manifest·데이터 형식은 바뀌지 않았다.
- 검증: 시험 모듈의 `assembleDebug`와 `lintDebug`가 성공했고 시험 모듈 lint는 문제 0건이다. 전체 `assembleDebug test lint`도 성공했으며 app debug/release/benchmark 각각 146개, 합계 438개 테스트가 실패·오류·건너뜀 없이 통과했다. app lint는 오류 0건과 기존 Gradle 업데이트 경고 1건이다. `ACTION_CREATE_DOCUMENT`에서 읽기 전용 루트는 저장 대상으로 표시되지 않았고, 제한 루트에는 저장 버튼이 활성화됐다. 50MiB 원문 포함 백업은 목적지 쓰기 중 `java.io.IOException: write failed: EPIPE`로 실패했고 앱은 `백업 실패`와 `선택한 위치에 백업을 저장하지 못했습니다. 저장 공간과 쓰기 권한을 확인하세요.`를 표시했다. 공급자에는 65,536바이트·SHA-256 `e89c84a35413540420b38cbf525fddb6fef448052916a89bf55949fbc6a7f7ba`인 불완전 `.wvb`가 남았고 시스템 열기 화면에도 65.54kB 파일로 보였다. 제품 APK manifest에는 시험 공급자 authority가 없고 별도 시험 APK에만 존재한다.
- 기기 확인: Android 16/API 36.1 에뮬레이터. 실패 뒤 50MiB 원본 SHA-256 `f94f99a8db19ff79ddebd1b4762acb8de9ebdca193e8b341223d6769ffcad696`가 유지됐다. 시험 공급자 데이터를 지워 불완전 파일을 제거하고 APK도 제거했다. benchmark 앱을 콜드 시작해 1,374ms에 같은 24,652블록·UTF-16 18,932,622자 문서와 읽기 위치 0.3%가 돌아왔고 crash 버퍼는 비어 있었다.
